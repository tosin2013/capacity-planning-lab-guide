By the end of this module, you will be able to:

[#the-scenario]
== The Scenario: A Deployment Gone Wrong

In the previous module you learned the *theory* of right-sizing — QoS classes, CPU throttling, P95-based resource requests, and HPA tuning. Now you will put those skills to work in a realistic scenario.

=== The Setup

Your team's `checkout-api` service was recently deployed to the `{namespace}` namespace. The developer who wrote the deployment manifest made two common mistakes:

[cols="2,3,3",options="header"]
|===
|Resource |What They Set |What's Actually Happening

|*CPU Request*
|`500m` (half a core)
|The service idles at 10–30m. Over 90% of the reserved CPU is wasted — blocking other pods from scheduling.

|*Memory Limit*
|`64Mi`
|The httpd process and its modules need 80–120Mi. The container is constantly approaching its limit and risks OOMKill under any load.
|===

[IMPORTANT]
====
*Why This Matters at Scale*:

This single deployment wastes ~940m CPU across its 2 replicas (requesting 1000m total, using ~60m). On a 3-node compact cluster with 24 vCPU total, that is *almost 4% of the entire cluster's CPU capacity* locked up by one small service.

Multiply this pattern across 50 services and you have a cluster that appears "full" while actually running at 15% real utilization. The operations team sees capacity alerts; the developers say "we're barely using anything." Both are right — and both are wrong.

*This module bridges that gap.*
====

=== Two Hats, One Dashboard

This lab uses a role-play structure. You will switch between two perspectives:

* *Ops Hat* (Platform Engineer): You monitor the fleet. Your job is to find the problem using dashboards and metrics — then communicate the evidence clearly to the development team.
* *Dev Hat* (Application Developer): You own the `checkout-api` code. When ops shows you the dashboard, your job is to understand the data, determine the correct resource values, and apply the fix.

The *dashboard* is the shared language between these two roles.

=== Part 3: Investigate the Evidence (Ops Hat)

With the dashboard loaded, systematically read each panel to build your diagnosis.

==== Panel 1 & 2: CPU and Memory Utilization Gauges

The top row shows utilization as a percentage of requests.

*What to look for:*

* *checkout-api CPU gauge*: Should show a very low percentage (5–15%). This means the pod is using a tiny fraction of its 500m CPU request — massive over-provisioning.
* *checkout-api Memory gauge*: May show a high percentage (close to or exceeding 100%). The 32Mi request is far below actual usage.
* *Other pods* (e.g., `load-generator`, `besteffort-app`): Compare their gauges to `checkout-api`. Well-sized pods typically show 40–80% utilization.

[NOTE]
====
*Why percentages matter more than absolute numbers*: A pod using 20m CPU with a 30m request (67%) is well-sized. A pod using 20m CPU with a 500m request (4%) is wasting capacity. The dashboard shows this ratio immediately — no mental arithmetic needed.
====

==== Panel 3 & 4: CPU and Memory Time-Series

The middle row shows requested vs actual usage over time.

*What to look for:*

* *CPU panel*: The "Requested" line for `checkout-api` sits at 500m. The "Actual" line hugs the bottom near 10–30m. The gap between these two lines is pure waste.
* *Memory panel*: Three lines per pod — Requested, Actual, and Limit. Watch for the "Actual" line approaching or touching the "Limit" line. If actual usage meets the limit, the kernel OOMKills the container.

==== Panel 5: Container Restarts (OOMKill Indicator)

This stat panel shows the total restart count per pod.

*What to look for:*

* If `checkout-api` shows restarts > 0, it has been OOMKilled. The 64Mi memory limit is too low.
* Compare against other pods — stable workloads should show 0 restarts.

==== Panel 6: CPU Throttling Rate

This panel shows how aggressively the kernel's CFS scheduler is throttling each pod.

*What to look for:*

* Despite the huge CPU request, `checkout-api` should show minimal throttling because the 1-core limit gives plenty of headroom. The problem here is waste, not throttling.
* Other pods with tighter limits may show higher throttle rates.

==== Confirm with CLI (Ops Report)

Back in the terminal, generate the numbers that support your dashboard observations:

[source,bash,role=execute,subs="+attributes"]
----
echo "=== Resource Configuration ==="
oc get deployment checkout-api -n {namespace} \
  -o jsonpath='  Requests: cpu={.spec.template.spec.containers[0].resources.requests.cpu}, memory={.spec.template.spec.containers[0].resources.requests.memory}{"\n"}  Limits:   cpu={.spec.template.spec.containers[0].resources.limits.cpu}, memory={.spec.template.spec.containers[0].resources.limits.memory}{"\n"}'

echo ""
echo "=== Actual Resource Consumption ==="
oc adm top pods -n {namespace} -l app=checkout-api

echo ""
echo "=== Pod QoS Class ==="
oc get pods -n {namespace} -l app=checkout-api \
  -o jsonpath='{range .items[*]}{.metadata.name}: {.status.qosClass}{"\n"}{end}'

echo ""
echo "=== Recent Events (OOMKills, warnings) ==="
oc get events -n {namespace} --field-selector involvedObject.kind=Pod \
  --sort-by='.lastTimestamp' 2>/dev/null | grep -i -E "checkout-api|oom|kill|back-off" | tail -5
----

[TIP]
====
*The Ops Report*: Share these findings with the development team. The message is:

_"Your `checkout-api` deployment is requesting 500m CPU per replica but using only 10–30m. That is 94–98% waste. Meanwhile, your 64Mi memory limit is below actual usage — you've had OOMKills. We need you to right-size this based on Prometheus data."_

This is the conversation that dashboards enable. Without the dashboard, ops says "the cluster is full" and dev says "we're not using anything." With the dashboard, both teams see the same numbers.
====

=== Part 4: Right-Size the Application (Dev Hat)

Now switch to the developer perspective. Ops has shown you the evidence. Time to fix the resource settings.

==== Step 1: Get P95 Recommendations

Use the `resource-right-sizer.sh` script from Module 3 to query Prometheus for the actual 95th-percentile resource usage:

[source,bash,role=execute,subs="+attributes"]
----
NAMESPACE={namespace} POD_SELECTOR="checkout-api.*" ~/module-03/resource-right-sizer.sh
----

The script will output:

* P95 CPU usage (raw millicores)
* P95 Memory usage (raw MiB)
* Recommended request and limit values
* The exact `oc set resources` command to apply

[NOTE]
====
*Cross-reference the recommendations with the dashboard*: The right-sizer uses Prometheus P95 data. The dashboard shows the same data visually. They should agree — the CPU recommendation should be far below 500m, and the memory recommendation should be well above 64Mi.

If the right-sizer reports 0 for CPU or memory, the deployment may not have been running long enough to accumulate metrics. Wait 2–3 minutes and re-run.
====

==== Step 2: Apply the Fix

Apply the right-sized values. Use the command output from the right-sizer, or apply the pre-built fixed manifest:

[source,bash,role=execute,subs="+attributes"]
----
oc set resources deployment checkout-api -n {namespace} \
  --requests=cpu=30m,memory=128Mi \
  --limits=cpu=100m,memory=192Mi
----

Wait for the rollout to complete:

[source,bash,role=execute,subs="+attributes"]
----
oc rollout status deployment/checkout-api -n {namespace} --timeout=60s
----

Confirm the new resource values:

[source,bash,role=execute,subs="+attributes"]
----
oc get deployment checkout-api -n {namespace} \
  -o jsonpath='requests cpu={.spec.template.spec.containers[0].resources.requests.cpu} memory={.spec.template.spec.containers[0].resources.requests.memory} | limits cpu={.spec.template.spec.containers[0].resources.limits.cpu} memory={.spec.template.spec.containers[0].resources.limits.memory}{"\n"}'
----

.Expected Output
[source,text]
----
requests cpu=30m memory=128Mi | limits cpu=100m memory=192Mi
----

==== Step 3: Verify the QoS Class

[source,bash,role=execute,subs="+attributes"]
----
oc get pods -n {namespace} -l app=checkout-api \
  -o jsonpath='{range .items[*]}{.metadata.name}: {.status.qosClass}{"\n"}{end}'
----

The QoS class should be *Burstable* (requests < limits). This is the recommended class for most production workloads — it allows CPU burst capacity while protecting against eviction.

==== Discussion: Policy Prevention

[IMPORTANT]
====
*What Could Have Prevented This?*

Platform engineers can prevent bad resource configurations before they reach production:

* *LimitRange*: Sets default and maximum resource values per container. A LimitRange with `max.cpu: 200m` would have rejected the 500m request at admission time.

* *ResourceQuota*: Caps total resource consumption per namespace. If the namespace quota was tight, the over-provisioned deployment would have failed to schedule.

* *Admission Webhooks / OPA Gatekeeper*: Custom policies can enforce right-sizing standards (e.g., "CPU request must not exceed 4x the P95 of similar workloads").

These guardrails work *with* dashboards, not instead of them. Dashboards catch existing problems; policies prevent new ones.
====

=== The Right-Sizing Conversation

[IMPORTANT]
====
*What Changed Between Module 3 and Module 4?*

Module 3 taught you the *mechanics* — QoS, throttling, P95, HPA. You worked alone on pre-existing workloads.

Module 4 taught you the *workflow* — how ops identifies a problem, communicates it with evidence, and how dev responds with data-driven fixes. The dashboard is the handoff artifact.

In real organisations, right-sizing is not a one-time script. It is an ongoing conversation:

1. *Ops* monitors dashboards for drift (CPU waste growing, memory limits approached)
2. *Ops* generates evidence (dashboard screenshots, CLI reports, P95 recommendations)
3. *Dev* reviews the evidence and adjusts resource requests in their deployment manifests
4. *Both* verify the fix on the dashboard
5. *Platform team* sets policies (LimitRange, ResourceQuota) to prevent regression

This loop is the operational discipline that makes capacity planning sustainable.
====

== Key Takeaways

* *Dashboards are the shared language* between operations and development teams
* *CPU over-provisioning* silently wastes cluster capacity — the cluster looks "full" while running at low utilization
* *Memory under-provisioning* causes OOMKills — the application crashes but the developer may not notice until production
* *P95-based right-sizing* is the data-driven alternative to guessing resource values
* *Policy guardrails* (LimitRange, ResourceQuota, admission webhooks) prevent future misconfigurations
